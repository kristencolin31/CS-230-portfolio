# CS 230 Portfolio Reflection

### Briefly summarize The Gaming Room client and their software requirements.

The Gaming Room wanted to expand their game, Draw It or Lose It, from an Android application to a web-based game that people could play on different devices. The game needed to support multiple teams and players while making sure each game, team, and player had a unique name. They also wanted everything managed through one game service.

### What did you do particularly well in developing this documentation?

I think I did a good job comparing the different operating systems and deciding which one would work best for the game. I looked at things like cost, security, and performance instead of just picking a platform I was familiar with. I also tried to explain my recommendations in a way that would make sense to the client.

### What about the process of working through a design document did you find helpful when developing the code?

The design document helped me understand how everything was supposed to work before getting too far into coding. The UML diagram was especially helpful because it showed how the Game, Team, and Player classes were connected. It also helped me understand why inheritance was useful and how the GameService class worked with the other classes.

### If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?

If I could improve one part, I would spend more time on the system architecture. I would add a diagram showing how the players, server, and database communicate with each other. I think that would make the design easier to understand, especially for someone who isn't familiar with the application.

### How did you interpret the user's needs and implement them into your software design? Why is it important to consider the user's needs?

I started by looking at what The Gaming Room wanted the game to do. Since they wanted players to access it from different devices, I recommended a web-based application using a Linux server. I also considered how the system would manage multiple players and keep game information organized. Understanding the user's needs is important because an application might work perfectly from a technical standpoint but still fail if it doesn't meet the client's expectations.

### How did you approach designing software? What techniques or strategies would you use in the future?

I approached the project by breaking everything into smaller parts. I started with the requirements, looked at how the classes would work together, and then compared the different operating systems. In the future, I would continue using UML diagrams and design documents because they help me stay organized and catch problems before getting too far into development.
